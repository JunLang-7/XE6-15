VoiceLife 牛牛｜20分钟演示讲稿
建议总时长：约 20 分钟；其中第 3 页包含现场操作与设备等待

使用提示
- 开场先讲清产品是什么，再用第 2 页说明结构与实体实现，第 3 页进入现场 Live。
- Live 的关键不是展示功能数量，而是让评委看见：儿童说出安排，设备确认并提醒，儿童说“知道了”，微信端出现“已消费”。
- 微信是家长观察和参与的辅助通道，不是儿童完成主流程的前置条件。
- 不宣称企业微信、飞书等尚未交付的渠道已经接入；不把“帮助儿童建立时间观念”说成已经验证的结果。

第 1 页｜概念图与产品定义｜0:45

各位评委老师、各位直播间的同学们，你们好，今天我们介绍 VoiceLife 牛牛。

VoiceLife 牛牛是一款挂在书包上的语音时间挂件。它不要求儿童先拿出手机，而是让儿童直接说出安排，牛牛负责记录、到点提醒，并把一次次处理结果留下来。

我们想做的不是功能更多的日历，而是一个儿童愿意带在身边、愿意开口对话的生活伙伴。

转场：产品定义之后，先看它如何从结构设计变成一个可以携带、可以装配的实体。

第 2 页｜产品结构｜0:55

这一页从三个角度看产品：它如何被携带、整机长什么样，以及内部怎样装配。

最左侧是使用场景。牛牛可以串在钥匙上、挂在书包上，跟着儿童进入每天的出行和学习场景；这不是摆在桌面上的工具，而是融入日常生活的陪伴设备。

中间是整机三视图。正面是屏幕、表情和交互区域；背面则留下了装配和维护空间。

最右侧是结构分解图。外壳、屏幕、主板和内部组件按装配顺序分层展开，外壳也是由我们的小组成员独立建模的。

这套外壳由灵构AI小组完成 3D 打印与整机装配，感谢灵构小组的鼎力支持。

牛牛不再只是概念图，而是一个可以拿在手里、挂在书包上继续验证的实体产品。

转场：接下来让牛牛闪亮登场。

第 3 页｜Live 演示｜1:00

转场：刚才的 Live 不是一个孤立动作，它把我们要解决的整条产品链路直接展示出来了。

第 4 页｜开场链路｜1:05

刚才的 Live 走过了五个连续节点。

第一，儿童说出来；第二，牛牛记下来；第三，到时间由设备端语音提醒，同时微信公众号发送提醒；第四，儿童说“知道了”完成处理；第五，微信端显示这条提醒已经被消费。

因此，家长既能在提醒到达时收到消息，也能在事后看到儿童有没有真正回应这次提醒。儿童完成一次处理，家长获得一次可观察的反馈。

这条链路把产品价值从提醒工具推进到了时间管理的陪伴工具。

转场：但这条链路首先要服务一个明确的人群。

第 5 页｜目标用户｜1:00

牛牛面向没有个人智能终端的小学生。他们有零散的学习和生活安排，能够用自然语言说出计划，也能听懂牛牛的简短确认。

儿童是日程的主要操作者：说出安排、处理提醒、根据变化做调整。家长不是替儿童完成每一步，而是通过微信观察结果、适时追问和鼓励。

所以，儿童不需要借用家长手机完成主流程；手机承担的是关联使用者的观察和辅助操作。

转场：我们再看现有方式为什么无法把这条路径完整交给儿童。

第 6 页｜现有方式｜1:15

纸条能记录，但刚想到时不一定在手边；普通闹钟会响，却不说明具体要做什么，也不方便处理“十分钟后再提醒”；家人转告最直接，却容易让儿童停留在被提醒状态；手机日历功能完整，却要求个人终端和多步点击。

这不是儿童有没有能力的问题，而是现有路径把操作门槛放在了儿童身上。

我们希望把“家长替儿童记住”，逐步变成“儿童自己说、自己确认、自己处理”，家长再根据真实结果参与培养。

转场：因此我们没有继续堆功能，而是主动收窄产品边界。

第 7 页｜产品取舍｜1:10

第一，语音优先。儿童用一句话创建、查询、修改和处理当前提醒。

第二，设备自包含。牛牛以书包挂件形态跟随儿童，主要流程由设备完成，不要求个人手机。

第三，IM 辅助。微信公众号保存创建回执、完整列表、提醒详情和消费状态，让家长能看见发生了什么。

我们主动不做完整日历 GUI、批量操作和复杂黑盒排程。功能少一点，是为了让最重要的路径真的能走完。

这也符合我们实训营规范说的，好的产品，是用最小的功能，实现最大化的需求覆盖。

转场：先看设备端如何把提醒变成一次可回应的对话。

第 8 页｜提醒设计｜1:25

设备语音是主通道。到点之后，牛牛说出时间和具体事项，小屏幕同步显示标题和状态。

儿童可以说“知道了”关闭当前提醒，也可以说“十分钟后提醒我”只推迟这一次。如果暂时没有回应，当前设计允许有限次数的自动推迟，避免一次错过就彻底失效。

微信在到点时同步发送提醒，不替代设备端的语音和屏幕；之后再保留详情，并把“已消费”这样的动作结果交给家长查看。

转场：设备端完成提醒之后，家长如何参与这次时间管理培养？

第 9 页｜家长协同｜1:30

儿童和牛牛负责把提醒真正处理掉：儿童说出安排，牛牛到点语音提醒，儿童说“知道了”关闭当前提醒。

微信回执把这个过程变成家长可观察的反馈。当设备收到“知道了”，IM 端会把对应提醒显示为“已消费”；如果没有处理，家长看到的仍是待处理状态。

这让家长有了一个更合适的参与方式：不是每次都替儿童设置闹钟，而是根据真实回执进行提醒复盘、追问和鼓励，把处理责任逐步交还给儿童。

家长看见“是否处理了”，儿童练习“自己处理”。这是微信辅助对产品价值的补充。

转场：因此，下面看家长在微信公众号里具体能看见什么。

第 10 页｜微信公众号协同｜1:25

左侧是设备绑定，建立家长观察入口；中间是日程摘要和详情，家长可以查看安排；右侧是提醒回执，重点看“知道了”之后状态变成“已消费”。

这不是让家长远程替儿童操作，而是通过真实回执参与提醒复盘、鼓励和习惯培养。

目前我们聚焦微信公众号。企业微信、飞书等渠道仍然保持在可扩展边界中。

转场：前面的产品链路不只存在于设计和服务端，我们已经把它装进了真实设备。

第 11 页｜从设计到实物｜1:20

我们已经在 ESP32-S3 开发板上完成设备侧全链路验证，并在灵构小组帮助下完成 3D 打印外壳和整机装配，这里就是我们设计图和实物之间的对比。

验证不只看“语音能不能响”，还覆盖多轮会话、音频与显示回归，以及 SQLite、FATFS 和复位恢复等存储链路。

这一步意味着牛牛不再停留在设计稿或 Demo，而是一个可以挂在书包上、进行语音交互的实体样机。

转场：实体样机能够稳定运行，是因为我们先把业务事实和设备、平台依赖分开。

第 12 页｜架构设计｜1:35

我们把系统分成三层。

第一层是领域核心：日程事实、定时任务和提醒状态。它们表达业务，不认识 ESP-IDF、SQLite 或微信。

第二层是应用编排：跨领域用例通过稳定 Port 协调日程、定时和通知，并用领域事件连接“到点触发”和“提醒送达”。需要原子性的地方，由应用层明确承诺，不靠调用顺序假装一致。

第三层是 Ports / Adapters：语音、SQLite/FATFS、ESP-IDF 和 IM Gateway 都在边界外，通过适配器接入。未来更换设备或新增渠道，核心业务不需要重写。

这个架构的价值不是模式名称，而是三个目标：可维护、可扩展、可验证。

其中，可维护意味着规则集中在领域与 Use Case，平台判断不扩散；可扩展意味着新增设备、存储或消息渠道，只需实现对应 Adapter，再补上契约测试；可验证意味着契约、事件、幂等和恢复路径都有边界，主机测试先行，实板只验证设备才能证明的行为。

转场：下面用一页完整架构图，把这些边界放回系统全貌中。

第 13 页｜当前架构图｜0:55

这张图是当前 VoiceLife 的整体架构参考。左侧是设备端的组件化模块单体，右侧是 VoiceLife 服务端的 IM Gateway，再向下连接微信公众号和未来的其他 IM 渠道。

大家可以重点看三条关系：第一，语音和 MCP 负责把儿童的一句话送进系统；第二，Schedule、TimingTask 和本地存储共同维护日程事实与提醒实例；第三，IM Application 和 Gateway 通过持久化、异步事件和动作回执，把“已消费”状态送回家长端。

这里能看到：前面讲的领域边界、Port 和 Adapter，在真实系统里已经对应到设备、云端和服务端的协作关系。

转场：这套架构不是一次性拼装出来的，而是按同一套规范过程逐步推进。

第 14 页｜规范实现过程｜1:55

这一页是我们对 XEngineer 方法的具体回答。XEngineer 里有三条判断，我们在 VoiceLife 里都找到了对应的工程落点：

先说产品做减法。产品 Proposal 没有从“提醒工具应该有多少功能”出发，而是把核心路径收窄成一句话：儿童说出来，牛牛记下来，到点用语音提醒，儿童说“知道了”完成处理。我们主动不做完整日历 GUI，也不要求儿童用个人手机完成主流程。这个判断先写进产品设计文档，再通过 Issue 和设计 PR 评审，而不是直接进入编码。

再说架构做乘法。架构设计文档把 Schedule、Timing、通知和设备平台的边界先定下来；核心只依赖领域和 Port，ESP-IDF、语音、SQLite、微信公众号等都放在 Adapter 或 Gateway。这样新增设备或渠道时，复用的是核心能力，而不是复制一套业务逻辑。

最后是测试必选。我们不是等功能做完才补测试，而是从 Issue 的验收条件写出 RED，再用最小实现进入 GREEN，重构期间保持通过；主机、契约、集成、E2E 和 HIL 各自验证自己能证明的范围。

落到流程上，就是 Proposal / Issue 定义问题与边界；产品、架构和实现草案先以文档和 PR 逐行评审，但按规范不合并，定稿后回到 Issue 作为编码起点；Design Issue 取舍，Contract 稳定模型和接口，TDD 完成最小实现，CI 与人工 Review 形成门禁，最后回到 ESP32-S3 用 HIL 日志、资源水位和回退结果收口。每个 Milestone 结束时，交付的不只是代码，而是可演示功能、测试结果和可复核证据。

这套流程不是为了增加仪式感，而是把“判断什么值得做、怎么做对、如何证明做得好”变成团队共同的工作方式。

转场：接下来用工程质量页收口，说明我们如何把规范变成可复核证据。

第 15 页｜工程质量｜1:00

接下来介绍一下我们的工程质量。

第一，单元测试。当前工作树的 C++ 主机测试一共 95 项，91 项标记为 unit，全部通过；IM Gateway 回归有 343 项，340 项通过、3 项跳过；Python 工具测试 198 项，197 项通过、1 项跳过。

第二，测试覆盖率。远程 main 的 Codecov 勋章给出总体 90%、C++ 90%、TypeScript 92%，project 和 patch 的目标是 80%。这说明覆盖率不是口头承诺，而是持续上传、持续检查的结果。

第三，CI 门禁。普通 PR 的 required checks 不是一个测试模块，而是一组自动化门禁：workflow-lint 检查工作流语法；clang-format 和 Ruff 检查格式与静态规则；Gateway、Host 和架构/Profile 检查验证主机行为；ESP-IDF 6.0.2 / ESP32-S3 job 验证默认固件可编译；dependency-review 做依赖漏洞和许可证审查，CodeQL 做 C++、Python、TypeScript 安全扫描。

第四，集成和契约测试。C++ 里有 4 项 integration 和 20 项 contract，验证 Schedule、Timing、Storage、IM 的组件拼装，以及 Port 的输入输出契约；边界还包括串口、Linx MCP 和 IM 契约解析。

第五，端到端测试。HIL E2E 固化日程 CRUD、提醒触发响应、IM 推送响应三条 journey；从设备事件到 Gateway、动作回执和“已消费”全链路状态，产出脱敏证据。

这里的质量门禁很具体：每项能力都要有测试结果、覆盖率和可复核证据。CI 失败时保留失败 job、阶段和分类；没有运行的 job 只写“未验证”，实板行为则以 HIL 的 artifact 和日志收口。

转场：工程质量把现在的基础夯实了，最后我们看牛牛下一步要走向哪里。

第 16 页｜未来展望｜1:00

我们已经有了可以运行的实体样机：设备侧语音日程闭环、微信公众号绑定查询与回执，以及对应的模块边界和实板验证。

下一阶段的重点不是继续堆功能，而是把产品放进真实生活里验证。我们会开展真实儿童试用，持续收集反馈，同时验证续航、耐用性、复杂环境声学和外壳交互。

“帮助儿童建立时间观念”是我们的产品目标，接下来要用真实使用检验它。我们希望把已经跑通的工程链路，逐步变成儿童愿意长期使用的陪伴体验。

转场：回到最开始的问题，牛牛最终想为儿童留下什么？

第 17 页｜结语｜0:45

我们希望儿童少记一些、少操作一些，把机械的记忆负担交给牛牛，同时自己说出计划、回应提醒、处理变化。

家长通过微信看见一次次“已消费”的提醒，不是为了替儿童完成生活，而是为了在合适的时候参与、鼓励，并逐步把时间管理交还给儿童。

VoiceLife 牛牛想做的不是一个功能更多的提醒工具，而是一个愿意被带在身边、愿意被开口呼唤的生活伙伴。

从一句话开始，用一次次真实回应，陪伴儿童建立自己的时间观念。谢谢各位老师。
